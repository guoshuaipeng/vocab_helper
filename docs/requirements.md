# 产品需求（单一来源）

> **所有人（含自动化迭代助手）读本仓库时，以本文件为准了解「接下来要做什么」。**  
> 路径：`docs/requirements.md`  
> 完成一项就勾选；新需求追加到对应优先级；大改动在「变更记录」留一行。  
> **未写 `docs/design-rN.md` 的主需求，不进入开发。** 设计方案须含：目标用户行为、信息架构、主流程、关键态、窄窗/全屏、文案、验收。

## 角色分工

| 角色 | Bot | 负责 |
|------|-----|------|
| 产品 | **单词产品设计** | 写/改本文件与 `design-rN.md` 主规格；定范围、排期、验收标准；bug 插队条目 |
| 交互 / UI | **单词UI设计** | 打磨交互与视觉；维护 `ux-guidelines.md`、补强 design 的 UI 细节；设计师验收（全屏/窄窗/深浅色）通过或打回 |
| 开发迭代 | **单词迭代** | 只按本文件 + 对应设计稿：开发 → 测试 → 交 UI 验收 → 复盘；不自创主需求 |
| 项目经理 | **单词项目经理** | 盯进度与阻塞；催产品/UI/开发持续迭代；协调验收与排期，不擅自改产品范围 |

用户新想法先跟「单词产品设计」说；界面打磨与空闲测优化找「单词UI设计」；落地后「单词迭代」实现；「单词项目经理」盯节奏防偷懒。不要每轮问是否继续。每轮未过 UI 验收不算完成。

## 怎么用

1. **产品/设计**：新需求或改范围 → 更新本文件 → 补 `design-rN.md` → 标「可开发」后交给迭代。
2. **排期 / 迭代**：每轮先打开本文件，从「进行中」取 1 个主需求 + 可选 1 个小抛光。
3. **实现后**：把对应条目改成 `[x]`；细节以当轮 `design-rN.md` 为准。
4. **用户新提需求**：先追加到本文件，再补设计稿，不要只写在聊天里。
5. **与其它文档**：`design-rN.md` = 交互+视觉；`retro.md` = 复盘；`ux-guidelines.md` = 持续设计约定；`backlog.md` = 历史镜像。
